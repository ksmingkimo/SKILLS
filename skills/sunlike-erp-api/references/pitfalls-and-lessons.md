# SUNLIKE ERP API 对接陷阱与教训

> 来源：ERP 订单数据采集系统（erp-connect）项目复盘（单据侧 8 坑）+ SKILLS 学习项目实测（报表侧 8 坑，2026-10 回填）
> 本文件记录了 SUNLIKE ERP API 对接过程中实际踩过的 16 个坑，每个都有错误做法、根因和纠正方法。

---

## 陷阱 1：API 路径缺少站点前缀

**错误**：`POST {站点}/auth/login`  
**正确**：`POST {站点}/SunReport/auth/login`（2026-09-30 站点迁移前为 `/ERPAPI/auth/login`——前缀以当前站点规范为准）

**根因**：凭用户的简化描述直接编码，没有打开文档核实路径。

**教训**：用户说"登录接口是 /auth/login"时，他说的可能是相对路径。SUNLIKE 所有 API 都在站点前缀路径下（历史 `/ERPAPI/`，2026-09-30 起 `/SunReport/`）。编码前必须用 Postman/curl 实际调用一次确认完整路径——**前缀会迁移，核实永不过时**。

---

## 陷阱 2：参数字段名大小写错误

**错误**：`{ username: "xxx", password: "xxx" }`  
**正确**：`{ USR: "xxx", PWD: "xxx" }`（大写 + 缩写）

**根因**：用过 RESTful API 的思维去套企业 ERP API。SUNLIKE 是老牌 ERP 系统，有自己的命名规范（大写缩写）。

**教训**：企业级系统（ERP/MES/WMS）的字段名必须以实际 API 文档为准，不能自行为参数命名。

---

## 陷阱 3：用 HTTP 状态码判断成功

**错误**：`if (resp.ok) { ... }`  
**正确**：`if (data.code === 0 && data.data && data.data.TOKEN) { ... }`

**根因**：SUNLIKE ERP API 无论业务成功还是失败，HTTP 层面都返回 200。

**验证方法**：用一个不存在的公司代号发登录请求，看返回——HTTP 200 但 `code` 是 -1。

---

## 陷阱 4：录入数据使用扁平结构

**错误**：
```json
{ "SO_NO": "xxx", "CUS_NAME": "客户", "PRD_NAME": "产品", "QTY": 1 }
```

**正确**：
```json
{
  "REF_NO": "...", "PGM": "DRPSO",
  "MF_POS": [{ /* 主表字段 */ }],
  "TF_POS": [{ /* 明细字段 */ }]
}
```

**根因**：ERP 单据天然是"主表 + 明细"嵌套结构，不能用 CRUD 思维去套。

---

## 陷阱 5：密码字段强制必填

**错误**：前端密码为空时提示"请填写完整连接信息"。  
**正确**：密码可以为空（内网部署常见）。

---

## 陷阱 6：查询缺少 PGM 和 OS_ID 参数

**错误**：`{ OS_NO: "SO68030001" }`  
**正确**：`{ PGM: "DRPSO", OS_ID: "SO", OS_NO: "SO68030001" }`

---

## 陷阱 7：每次调用都重新登录

**错误**：每次查询/录入前都调用 `login()`。  
**正确**：同站点地址 Token 缓存复用。配置变更时清除缓存。

---

## 陷阱 8：金额字段 AMT 不传或传 0

**错误**：只传 QTY 和 UP，让 ERP 自己算。  
**正确**：`AMT = QTY × UP` 在客户端计算后传入。AMT 和 AMTN 都是必填字段。

---

## 核心教训

> **"应该是"三个字是 bug 的摇篮。**
> 对接第三方系统时，只有"文档怎么写"和"实测怎么返回"。

---

## 对接前自查清单

- [ ] 完整 API 路径已用 Postman/curl 验证
- [ ] 所有参数字段名与文档完全一致
- [ ] 成功判断条件已验证（非仅 HTTP 状态码）
- [ ] 请求体结构已确认（扁平 vs 嵌套）
- [ ] 每个字段的必填/可选已向文档确认
- [ ] 用错误参数测试过错误返回格式
- [ ] Token 有缓存机制
- [ ] 金额字段在客户端已正确计算

---

**第二部分：报表侧陷阱（2026-10 回填，来源：SKILLS 学习项目实测）**——报表 API 与单据 API 是两套请求体（见 `report-api.md`），坑单独成列。

## 陷阱 9：报表成功判断看 HTTP 状态码

**错误**：`resp.ok` / HTTP 200 当成功。  
**正确**：`response.code === 0`。

**根因**：与单据 API 同源——ERP 业务失败也回 HTTP 200；报表侧另有独立错误码体系（10001 / 20001 / 20004）。

**教训**：`code === 0` 是唯一成功标准；10001 的 message 仅供参考不可靠。

---

## 陷阱 10：SEARCH_INFO 随意排序 / 空筛选传 null

**错误**：按 JSON 习惯自由排序格子；空筛选传 `null`。  
**正确**：按索引固定顺序；空筛选传 `""`。

**根因**：SEARCH_INFO 是位置敏感的格子数组（getReport 十格 / getList 八格 / 流式三格，语义各不相同）；后端对 null 直接报 10001「Value cannot be null」。

**教训**：请求体结构照实测配置抄；换报表先查该报表的格子布局（`report-api.md`）。

---

## 陷阱 11：响应列名按请求自造

**错误**：按请求的 DISPLAY_FIELDS 取列名渲染。  
**正确**：用实际返回的行对象键 `Object.keys(rows[0])` 自适应。

**根因**：实测请求 28 列、返回 29 列且列名不同（invso）；账簿清单请求 18 列、返回 35 列。

**教训**：列名以 ERP 实际返回为准，绝不自造。

---

## 陷阱 12：分页传 offset 翻页

**错误**：按传统分页传 offset/page 翻页。  
**正确**：getReport 取全量 `[0, 5000]`；getList 顶层 `PAGE_INFO: { PAGE_SIZE: -1 }`。

**根因**：服务端无视 offset 的 start（一刀切取全量）；getList 家族分页在顶层、无 5000 截断。

**教训**：达到 5000 行上限提示截断、建议缩小筛选，而不是翻页。

---

## 陷阱 13：筛选参数键名大小写写错 → 静默失效

**错误**：参数解析产小写键（`cusno`），构造请求体读 camelCase（`cusNo`）→ 恒为 undefined → 空筛选 → 返回全量，看起来「筛了」。  
**正确**：键名全链路统一；验证筛选用**不存在的值**（期望 0 行）。

**根因**：用真实值验证会误判——C001→9 行恰等于全量 9 行，分不清筛没筛。

**教训**：验筛选必须用不存在值（如 `ZZZZ` → 0 行）。

---

## 陷阱 14：SSE 流式把进度当结果 / 不判 Content-Type

**错误**：把流里的进度当最终结果；按 chunk 直接 split 行；不判 Content-Type。  
**正确**：三路判别（HTTP 错 / `application/json` 业务错 / `text/event-stream` 流式）；行缓冲解析；`ERR` 字段转可读错误；进度只进 stderr。

**根因**：chunk 边界会切断行；失败时后端不走流、直接回 JSON。

**教训**：进度不是结果——数据在 `DATA.REPORT__TAB`，可能分多条消息，拼起来才是最终行集合。

---

## 陷阱 15：并发登录炸池

**错误**：多路同时调用 login。  
**正确**：认证层内置单飞保护——同一时刻最多一个登录请求。

**根因**：并发登录撞坏 .NET 内部非并发集合 → 10001「concurrent update … corrupted its state」，且**进程内状态持久损坏**（此后单发请求也全炸）。

**教训**：预防 > 恢复；炸池后唯一恢复手段是回收应用池（见下方「后端行为怪癖」）。

---

## 陷阱 16：Token 过期直接报错放弃

**错误**：报错退出，让用户手动重登。  
**正确**：20001/20004 → 清 Token 缓存重登重试一次；仍失败再提示手动登录。

**根因**：认证失效码与业务错码不同，可自动区分处理。

**教训**：重试一次是标配；Token 缓存提前 1 分钟过期判定，避免用到临期 Token。

---

## 后端行为怪癖（报表与单据通用，2026-10 实测）

1. **冷启动**：重启/闲置后首个请求预热可能 >10s → 首次调用报 NETWORK 属正常，稍后重试即可；**并发打冷后端 = 全员超时**——遇「全炸」先单发请求捂热，别急着怀疑代码
2. **PowerShell 5.1 + curl.exe 传 JSON 搅坏双引号**：实测报 10001「Value cannot be null」，同请求 Git Bash curl / Node fetch 成功 → 发 JSON 请求用 Git Bash 的 curl、Node fetch 或 Invoke-RestMethod
3. **应用池回收**（并发登录炸池后的唯一恢复手段）：本机站点在 Default Web Site 下，池名 `AppPool_SunReport`：`Restart-WebAppPool -Name 'AppPool_SunReport'`
